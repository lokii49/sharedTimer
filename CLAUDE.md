# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

SharedTimer — iOS SwiftUI app for timers and date countdowns that can be shared via iMessage. Xcode project at `sharedTimer/sharedTimer.xcodeproj`. No SPM packages, no CocoaPods — pure Xcode targets.

## Build / test / run

Requires Xcode + a Mac. From `sharedTimer/`:

```
xcodebuild -project sharedTimer.xcodeproj -list          # list targets/schemes
xcodebuild -scheme sharedTimer -destination 'platform=iOS Simulator,name=iPhone 17' build
xcodebuild -scheme sharedTimer -destination 'platform=iOS Simulator,name=iPhone 17' test
xcodebuild -scheme sharedTimer -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:sharedTimerUITests/sharedTimerUITests/testExample test
```

Schemes: `sharedTimer` (main app), `sharedTimerClip` (App Clip), `sharedTimerMessages` (iMessage extension), `sharedTimerWidget` (widget/Live Activity — embedded, not independently runnable), `sharedTimerWatch` (Watch app + nine Watch tests; embeds `sharedTimerWatchWidget`). Prefer opening the project in Xcode and running on a simulator/device for anything involving notifications, Live Activities, or the Messages extension — those don't function meaningfully under plain `xcodebuild test`.

`sharedTimerTests` has 135 Swift Testing (`import Testing`) tests: `sharedTimerTests.swift` (51) covers `TimerModel` (URL round-trip + back-compat incl. `upd`, JSON decode, sequence math + pre-armed window, `targetDate`), `TimerStore` decode/prune/registries, `CloudLinkStore` tombstones, `RecentTimersStore`, and Siri selection/state guards; `TimerSpotlightTests.swift` (6) covers metadata, expiry, ID routing, and real-index update/delete/reconciliation in an isolated domain; `SharedSequenceTests.swift` (12) covers sequence links/CloudKit mapping, validation, catch-up, scheduled starts, pause, and notification windows/exclusions. `AnnualCountdownTests.swift` (16) covers annual Gregorian/time-zone/leap/DST projection, sharing/CloudKit, pause/extend, notifications, Calendar event mapping and permission/error/search behavior. `WhatsNewTests.swift` (6) covers the What's New version gate. `EditTimerTests.swift` (9) covers `TimerPayload.edited` (rename/toggles, countdown start preservation, paused/sequence no-ops, annual re-anchoring incl. the clamped-leap-day rename, link round-trip). `TimerWidgetTests.swift` (8) covers widget state/selection, ID-only links, planned timeline boundaries, coarse refresh, and static layout attachments; `AlarmKitDeviceTests.swift` (27, incl. the stray-alarm sweep and two Siri-intent integration tests) runs against real AlarmKit on device only — run the unit and AlarmKit suites separately (see Siri / Shortcuts below) and grep for `Test run with`, since xcodebuild's XCTest summary line misleadingly reports "Executed 0 tests". `sharedTimerTests/AlarmKitDeviceTests.swift` schedules **real** AlarmKit alarms and reads them back (pre-armed sequence window, cancel ranges, legacy-id migration, delete/end teardown) — skipped unless AlarmKit is authorized, i.e. it only runs on a physical device where "Allow" was tapped (`-destination 'id=<UDID>'`, find it with `xcrun devicectl list devices`). Each test must `await tearDown()` — an un-awaited `defer { Task {…} }` left real alarms ringing on the device once; `sweepStrayTestAlarms()` cancels any alarm no stored timer owns. Swift Testing `-only-testing` filters need the trailing `()` on a test name. `sharedTimerClipTests` is empty boilerplate; `sharedTimerUITests` retains the two default launch tests and adds timer-link deletion safety plus scheduled shared-sequence import → Start Now → Pause → Extend → Resume → Delete. The annual import/Next Year/pause/extend/resume flow, creation form, and real Calendar access/retry are also tested. Timer flows remove their temporary quiet timers. CloudKit delivery, notification presentation, and Live Activity rendering still require manual checks on a simulator/device.

## Architecture

Five app targets share one data model through a **`Shared/` synchronized folder** (not a Swift package — each target compiles its own copy of the same source files, no `public` needed):

- `sharedTimer/` — main app (list of timers, create/pause/resume/extend/delete)
- `sharedTimerClip/` — App Clip, opened via the `t.html` share link; shows a single live countdown
- `sharedTimerMessages/` — iMessage extension; compose-and-share sheet plus a running view shown when a shared link/card is opened inside Messages
- `sharedTimerWidget/` — WidgetKit extension: home-screen widget (`SharedTimerWidget.swift`) + Live Activity / Dynamic Island (`TimerLiveActivityWidget.swift`), bundled via `SharedTimerWidgetBundle`
- `sharedTimerWatch Watch App/` — watchOS companion app, embedded in `sharedTimer`. Thin `WatchConnectivity` mirror, not a peer — see "Watch app" below.
- `sharedTimerWatchWidget/` — Watch complication and Smart Stack extension, embedded in the Watch app.
- `WatchShared/` — Watch-only model, snapshot cache, deep links, and widget layouts shared by the two Watch targets.

`sharedTimer/Shared/` holds the files shared by the four iOS targets: `TimerModel`, `TimerStore`, `Sky` (app, Clip, Messages, Widget); `NotificationScheduler`, `AlarmPlayer` (app, Clip, Messages); `TimerActivityAttributes` (app, Messages, Widget); `LiveActivityController`, `TimerFieldsView`, `CloudLink`, `CloudSyncController`, `DisplayNameStore` (app, Messages — the two targets that mutate a shared timer a person is looking at); `TimerAlarmMetadata` (app, Widget). The `Shared` group is listed in each of those four targets' `fileSystemSynchronizedGroups`; which target compiles which file is controlled by that target's `PBXFileSystemSynchronizedBuildFileExceptionSet` for the `Shared` folder in `project.pbxproj` (the **exclusion** list — the main app has none, it compiles everything). A new file dropped into `Shared/` is compiled by **every** one of those four targets unless added to the other three exception lists — check before adding anything that imports AlarmKit/CloudKit/UIKit-only APIs (the Widget must stay network- and AlarmKit-free). To verify membership after a project change, build each scheme and inspect `*.SwiftFileList` under DerivedData. Previously these were copy-pasted per target and kept in sync by `diff`; that's gone — one edit now lands everywhere.

**Exception: `WatchShared/TimerModel.swift`** is its own, deliberately different file (no `TimerStore`/`NotificationScheduler`/`LiveActivityController`/sequence types — see "Watch app" below). It is not in `Shared/`; port `TimerModel` changes to it by hand only when the watch actually needs them.

`TimerFieldsView.swift`'s `kindLocked` (default `false`) collapses the "Timer/Countdown" `Picker` to a read-only row: the main app's `NewTimerSheet` always passes `true` since the "+" menu (or a Quick Action) already asked timer-vs-countdown before the sheet opened — re-showing the picker there just re-asked an answered question. `sharedTimerMessages`'s `TimerComposeView` leaves it at the default, since its single compose flow never pre-picks a kind.

`CloudSyncController.swift` carries four non-obvious CloudKit gotchas, each cost real debugging time to find and each is easy to silently reintroduce:

- **Never use `CKContainer.default()`.** It's documented to resolve the container from the `com.apple.developer.icloud-container-identifiers` entitlement array, but that lookup was observed to fail specifically inside the Messages extension's sandbox — even with the entitlement correct in the source file, Xcode's Signing & Capabilities, and the Developer Portal App ID capability — silently falling back to CloudKit's own undocumented last-resort default (`"iCloud." + bundle identifier`, e.g. `iCloud.com.lokesh.sharedTimer.sharedTimerMessages`, which isn't a real container) and failing every operation with `CKError "Bad Container"` (5/1014). Use the explicit `private static let container = CKContainer(identifier: "iCloud.com.lokesh.sharedTimer")` instead, everywhere.
- **`CKShare.url` is never populated on the local object you constructed and passed to `CKModifyRecordsOperation`**, even after a successful save — `modifyRecordsResultBlock` only reports overall success/failure, it never updates the records you passed in. The server-assigned fields (including the share URL) only exist on the record `perRecordSaveBlock` hands back; read `.url` from that saved instance, not the original `share` variable. Same split applies to per-record *failures*: the overall operation can report `.success` while a specific record (e.g. the share, if its root record already has one attached — CloudKit allows only one share per record) failed — that's only visible in `perRecordSaveBlock`, never in `modifyRecordsResultBlock`.
- **`ensureZoneExists` does not cache "already created" locally.** It used to (a flag in App Group `UserDefaults`, set once after the first success), but that cache goes stale the moment the target container changes — e.g. exactly the `CKContainer.default()` fix above, where the flag stayed `true` from whatever container `.default()` used to resolve to, silently skipping zone creation against the *new* container forever after and producing `CKError "Zone Not Found"` (26/2036) that looks like an unrelated fresh bug. `CKModifyRecordZonesOperation` saving a zone that already exists is a documented safe no-op, so it always actually calls through now. Don't reintroduce the cache.
- **The database change token is saved only after every changed zone's records were fetched** — never in `changeTokenUpdatedBlock`/the db op's success path. Saving it earlier meant a failed zone fetch was never retried (the next pull started past the change that named that zone). `CKError.changeTokenExpired` (db or zone level) clears that token and refetches once from nil; without it the stale token fails every pull forever and sync silently dies. `zoneNotFound`/`userDeletedZone` (and an overall `.partialFailure` wrapping them) must not hold the db token back.

`Shared/AlarmPlayer.swift` (loops the bundled `alarm.caf` via `AVAudioPlayer` on a `.playback`-category session, so it ignores the silent switch like a native alarm) is compiled by `sharedTimer`/`sharedTimerMessages`/`sharedTimerClip` only — the three targets with a foreground countdown view and `NotificationScheduler.swift`. `NotificationScheduler` also points `content.sound` at `alarm.caf` instead of `.default`, so a resting notification uses the same tone as the foreground loop. `alarm.caf` itself is a resource and still lives once per target folder (`sharedTimer/`, `sharedTimerClip/`, `sharedTimerMessages/`).

On iOS 26 a payload AlarmKit owns (`AlarmController.ownsAlert`, below) gets AlarmKit's own full-screen alert (foreground included), so `ContentView` only sounds the in-app `AlarmPlayer` loop when `AlarmController.shouldSoundInAppAlarm(for:)` is true: the alarm toggle is on but AlarmKit permission is **not** granted. A payload AlarmKit is handling never triggers the loop — deliberately keyed on auth state, not `AlarmManager.alarms` membership, because a stopped-from-the-panel alarm leaves the list and would otherwise re-bang the in-app loop the next time the app opens.

`VibrationPlayer` (same file as `AlarmPlayer`, same 3-target footprint) is a second, independent foreground loop for `TimerPayload.vibrationEnabled` (the compose-sheet "Vibrate" toggle, under the "When it ends" section) — a repeating `kSystemSoundID_Vibrate`. In the main app it's a **fallback only**: `AlarmController.shouldVibrateInApp(for:)` gates it to "vibration wanted, AlarmKit not authorized" (mirroring `shouldSoundInAppAlarm`), because a payload AlarmKit owns already vibrates via its own full-screen alert — starting `VibrationPlayer` too would double-buzz live and re-buzz with a stale "Stop" banner on every reopen (`TimerStore.isFinishAcknowledged` also gates this — see below). In `sharedTimerMessages`/`sharedTimerClip`, which never reach `AlarmController`, `VibrationPlayer` is the **only** mechanism and runs unconditionally off `vibrationEnabled` — grep every `AlarmPlayer` start/stop site together with its `VibrationPlayer` counterpart before changing the finish-handling flow.

`TimerStore.acknowledgeFinish(id:)` / `.isFinishAcknowledged(id:)` (App-Group-backed, alongside `save`/`loadAll`) record "Stop" was tapped for a specific finish — cleared automatically on the next `TimerStore.save` for that id (repeat, extend, etc.), since a new mutation means a future finish should be free to alert again. Written by the vibration-only notification's "Stop" action (see below) and the in-app Stop button; read by `shouldVibrateInApp`.

`Shared/TimerAlarmMetadata.swift` (the `AlarmMetadata` payload on an AlarmKit alarm) is compiled by `sharedTimer` (schedules the alarm) + `sharedTimerWidget` (renders its Live Activity) only.

### Core model (`TimerModel.swift`)

- `TimerPayload` — the one data type for both timer and countdown modes (`TimerKind`). Holds `endDate`, `duration`, optional `pausedRemaining` (non-nil = paused). `remaining`, `isExpired`, `progress(at:)`, `paused()`, `resumed()`, `extended(by:)` are all pure, date-parameterized functions — no wall-clock reads except through the `at:`/default-`Date()` args, which keeps them usable inside `TimelineView`.
- `TimerPayload.url()` / `.from(url:)` encode/decode a payload into query params on `https://lokii49.github.io/sharedTimer/t.html` — this is the link shared in Messages and opened by the App Clip. Wire params: `id`, `label`, `end`, `dur`, `kind`, `paused` (only if paused), `alarm` (only `alarm=0`, i.e. only when the alarm toggle is off — absent means on, safe because "alarm on" never changed meaning). `vib` is **not** the same convention — it's always emitted explicitly (`vib=1`/`vib=0`), and absent means *off*: since vibration-on now also triggers a full-screen AlarmKit takeover (not just a foreground buzz), a link from before the toggle existed can't be allowed to default to it the way `alarm` does. Same asymmetry in `TimerModel.swift`'s JSON `Decodable` init (`alarmEnabled` back-compats to `true`, `vibrationEnabled` to `false`) and `CloudSyncController`'s record decode. `upd` (1.0.4) is the payload's `updatedAt` stamp (epoch seconds, emitted only when known) — set by every *user* mutation (`paused`/`resumed`/`extended`/`repeated`/`materializingPhase`, compose, Stop), never by re-derivation (`advancedSequence`). An already-known timer adopts a re-opened link's snapshot only via `TimerPayload.shouldAdopt` (strictly newer stamp; an unstamped link never wins, so an old link can't roll back newer state), and only for timers **without** a CloudLink — CloudKit sync is authoritative for those. Applied in `ContentView.handleIncoming`, `MessagesViewController.presentView` and the Clip's `handle`; `docs/t.html` ignores `upd` (it only renders). Changing the payload's wire fields requires updating `docs/t.html`'s JS parsing (`qs(...)` calls) in lockstep.
- `TimeFormat` — day-aware duration formatting (`3d 04:12:09` / `4:12:09` / `12:09`) shared by every surface; also duplicated in `docs/t.html`'s `formatRemaining`/`formatTargetDate` JS.

### Persistence & cross-target sync

`TimerStore` reads/writes an array of `TimerPayload` as JSON in `UserDefaults(suiteName: "group.com.lokesh.sharedTimer")` — the App Group is what lets the main app, Messages extension, App Clip, and widget all see the same timers. Every target's entitlements file must list that same group ID. `TimerStore.persist` prunes payloads that are non-paused and expired more than 24h ago.

### Notifications, Alarms & Live Activities

Deployment target is **iOS 26.1** (all shipping targets — bumped from 17.0 for AlarmKit).

`TimerPayload.alarmEnabled` (the compose-sheet "Alarm" toggle, under "When it ends", default true, in `TimerFieldsView`) gates the whole loud path: when **false**, a finished timer/countdown raises only a `.default`-sound notification — never AlarmKit, never the in-app `AlarmPlayer` loop. It's a payload field → carried in the share link (`alarm=0`, emitted only when off), CloudKit (`alarmEnabled` record field), and decoded back-compat as `true` everywhere. `docs/t.html` reads `alarm` into a body data-attribute only (no audio there). `StartTimerIntent` / `StartCountdownIntent` expose it as an `alarm` parameter.

`TimerPayload.vibrationEnabled` (the compose-sheet "Vibrate" toggle, default true, same `TimerFieldsView` section) has the same wire/CloudKit/back-compat/Intent treatment as `alarmEnabled` (`vib` param, `vibrationEnabled` CloudKit field, `vibrate` Intent parameter) but is its own toggle — on with the alarm off, or off with the alarm on, are both real combinations.

Finished-alert mechanism is chosen **by `AlarmController.ownsAlert(for:)`** (`payload.alarmEnabled || payload.vibrationEnabled`) — not by kind; both `.timer` and `.countdown` route the same way:

- **Either toggle on → AlarmKit** (`sharedTimer/AlarmController.swift`, **main app target only**). Full-screen through the silent switch and Focus, Stop / Repeat panel, survives a force-quit, even locked — the same experience regardless of *which* toggle triggered it. `alarmEnabled` picks the loud `alarm.caf`; vibration-only (alarm off) picks `vibration_silent.caf` (`sharedTimer/vibration_silent.caf`, a digitally-silent `.caf` — all-zero samples — matching `alarm.caf`'s format/duration; regenerate with `ffmpeg -f lavfi -i anullsrc=r=44100:cl=mono -t 3.03 -sample_fmt s16` piped through `afconvert -f caff -d LEI16@44100 -c 1` if it's ever lost). AlarmKit's `sound:` is **non-optional with no explicit "no sound" case** — checked against the real `AlarmKit`/`ActivityKit` `.swiftinterface` in the SDK, `AlertConfiguration.AlertSound` only has `.default`/`.named(_:)` — so silence is smuggled in as a named asset instead. **Confirmed on a physical device**: AlarmKit's alert vibration isn't decoded from the sound file's waveform, same as a regular notification's haptic firing independent of which sound plays — `vibration_silent.caf` rings full-screen with vibration and no audible tone, exactly as designed. AlarmKit also runs its **own** Live Activity (rendered by `sharedTimerWidget/TimerAlarmActivityWidget.swift` via `AlarmAttributes<TimerAlarmMetadata>`, carrying `kind` so the icon/tint match `.timer` vs `.countdown`), so the custom `TimerActivityAttributes` Live Activity is **not** started when AlarmKit owns the alert — starting both is the "too many Live Activities" bug. The "Repeat" button uses AlarmKit's built-in `.countdown` secondary-button behavior (no App Intent); `AlarmController.reconcileRepeat` folds a Repeat back into `TimerStore` on next foreground (not filtered by kind or which toggle triggered it — a repeated countdown restarts its original `duration` from now, same as a timer).
- **Both toggles off → `NotificationScheduler`** + custom `TimerActivityAttributes` Live Activity, for either kind. A quiet, standard-sound notification, no AlarmKit involvement.
- **AlarmKit denied/unavailable, either toggle on → `NotificationScheduler` fallback.** If `vibrationEnabled` (alarm off) is what wanted AlarmKit, this fallback notification also gets `NotificationScheduler.vibrationFinishCategoryID` — lock-screen "Repeat"/"Stop" `UNNotificationAction`s, registered + handled only in `AppDelegate` (`UNUserNotificationCenterDelegate`). "Stop" doesn't interrupt anything active (`VibrationPlayer`/`AlarmPlayer` are foreground-only, and no third-party app can vibrate in the background on iOS — confirmed platform limit, not a gap) — it calls `TimerStore.acknowledgeFinish` so the app doesn't auto-re-buzz on next open. "Repeat" runs the same repeat-mutation sequence as everywhere else. Setting the category identifier is harmless in the `sharedTimerMessages`/`sharedTimerClip` builds of `NotificationScheduler.swift` too (their notifications are the **primary**, not fallback, path there, since they never reach `AlarmController`) — an unregistered category just renders with no action buttons.

(Countdown-through-AlarmKit, and vibration-through-AlarmKit, are both deliberate product choices, not the platform default — a far-out date target ringing/buzzing full-screen when it finally arrives is the whole point of turning either toggle on. If a future change wants either case to stay gentle/backgrounded regardless of the toggle, that's a reversion of this decision, not a bug fix.)

`NSAlarmKitUsageDescription` lives **directly in `sharedTimer/Shortcuts.plist`** (the `INFOPLIST_FILE`), not as an `INFOPLIST_KEY_*` build setting — Xcode 26's `INFOPLIST_KEY_*` allowlist silently drops that key, so the setting compiled away and no permission prompt ever showed. Verify with `plutil -p <built>.app/Info.plist | grep Alarm` after touching it.

`AlarmController` is **main-app-only on purpose** (lives in `sharedTimer/`, not `Shared/`): AlarmKit is unavailable in app extensions, so `sharedTimerClip` / `sharedTimerMessages` stay wholly on the `NotificationScheduler` path regardless of `alarmEnabled`/`vibrationEnabled` — a shared/opened timer never rings/buzzes through AlarmKit unless it's also open in the main app. If AlarmKit is denied / unavailable / at capacity, `AlarmController.reschedule` falls back to `NotificationScheduler` for that payload too. `AlarmController` must never be reachable from `TimerStore.swift` (same invariant as `CloudSyncController` / `WatchSyncController` — `TimerStore` compiles into the Widget); `AlarmController` reaching *into* `TimerStore` (for `isFinishAcknowledged`) is fine, only the reverse direction is forbidden.

The main app's mutation sites all funnel through `TimerArming.arm(_:)` (`sharedTimer/TimerArming.swift`; `armAwaiting` for intents) — `AlarmController.reschedule`, then the custom Live Activity only `if !AlarmController.ownsAlert(for: payload)`: `ContentView.armAlerts` (`onAppear`, `apply`, `pullCloudChanges`), the `AppDelegate` push handler and vibration-notification Repeat, the `WatchSyncController` watch-relay, and both start intents. Change the routing there, not at the call sites.

**AlarmKit-armed registry (`TimerStore.setAlarmKitArmed`/`isAlarmKitArmed`, App Group).** `AlarmController.performReschedule` marks an id armed only after AlarmKit accepts its alarm (cleared first on every reschedule, and by `clear`, `cancelSequenceAlarms`, `TimerStore.delete`). The Messages extension's bubble-open path (`presentView`, `acceptShareIfNeeded`) and the Clip's `handle` skip their own notification + custom Live Activity for an armed id — before this, opening the bubble of a timer the main app owns through AlarmKit stacked a second alert and a second Live Activity on top. **Mutations made inside Messages (`persist`) still arm unconditionally** — the extension can't move the AlarmKit alarm, so until the main app next foregrounds and re-arms (its `armAlerts` loop cancels that notification by id), an extend/pause done in Messages can leave AlarmKit ringing at the old time alongside the new notification. Platform limit (no AlarmKit in extensions), not a bug to "fix" by skipping the notification. `TimerArming.arm` also ends any custom Live Activity for an AlarmKit-owned id, cleaning up one an extension started earlier.

`sharedTimerMessages/MessagesViewController.swift` still reimplements the older "cancel notification → reschedule → start/update/end Live Activity" sequence directly (never reaches `AlarmController` — no AlarmKit in extensions) — grep it before changing the mutation flow. `sharedTimerClip` carries no `LiveActivityController.swift`/`TimerActivityAttributes.swift` at all and its `ContentView.swift` has no Live Activity code whatsoever (confirmed by grep, 2026-09 audit) — a shared timer opened in the App Clip gets no custom Live Activity, full stop. An earlier version of this doc claimed otherwise; that was doc drift, not a description of a real regression — treat "Clip has zero Live Activity involvement" as the current, correct state unless a future change deliberately adds it. `NotificationScheduler.swift` also pre-arms an eight-phase notification window for shared sequences and excludes occurrences already covered by AlarmKit (see below).

**Extend-awareness notification** (`AppDelegate.notifyIfExtended`, main app only): the silent `CKDatabaseSubscription` that drives all CloudKit sync (`shouldSendContentAvailable = true`, no alert) has zero visible signal on its own — a participant who isn't looking at the app has no way to know someone else just extended a shared timer. The push handler snapshots `TimerStore.loadAll()` *before* applying the batch's saves, then diffs each incoming payload against its prior local copy: a pure extend (`endDate` moved forward ≥5s, `duration`/pause state unchanged, `existing.remaining > 0` so a same-shaped repeat from a finished timer doesn't also match) fires a local notification via `CloudSyncController.fetchAttribution` for the "who". This deliberately needs no new CloudKit field and no attribution plumbing through `pullChanges` — the delta comparison doubles as self-echo suppression for free, because `ContentView.apply` always calls `TimerStore.save` *before* `CloudSyncController.pushUp`, so a change's own round-trip back through the subscription always diffs to zero against what's already stored locally. Scoped to extend only (not pause/resume/delete) — those are much more frequent and would make this noisy. `AppDelegate` also gained `userNotificationCenter(_:willPresent:)` (previously absent, so ANY foregrounded notification showed nothing) — gated by category so only this new notification gets a foreground banner; finish/vibration-fallback notifications keep their existing silent-in-foreground behavior, since the in-app UI already covers that case for them.

### Live Activity buttons (`Shared/LiveActivityIntents.swift`, `sharedTimer/LiveActivityActions.swift`)

Both Live Activities — AlarmKit's (`TimerAlarmActivityWidget`) and the custom one (`TimerLiveActivityWidget`) — show `LiveActivityControls` (`sharedTimerWidget/LiveActivityControls.swift`) on the Lock Screen and in the expanded Dynamic Island: **Pause/Resume** (`SetTimerPausedIntent(timerID:paused:)` behind a plain `Button(intent:)` in `PauseToggle` — it carries the desired state, so it's idempotent. **Don't make it a `SetValueIntent` behind `Toggle(isOn:intent:)`**: tried for instant optimistic feedback, it rendered fine but never paused anything on device, even with the style routing taps through `configuration.isOn` — most likely performed in the widget process, where `LiveActivityActions` is the no-op stub. The widgets' time text uses `.invalidatableContent()` instead, so it shimmers while the update is in flight) plus **✕** (`StopTimerIntent`: ends a plain timer now, silently — it moves to Finished with Repeat, it is *not* deleted). On an AlarmKit sequence-phase card the second button is **Next** (`AdvanceSequenceIntent`, carrying the phase's global index) or, on the final phase, **Cancel** (`EndSequenceIntent`) — the same pair as the phase alert's secondary button. The card reads that from `TimerAlarmMetadata`'s optional `sequenceCaption`/`phaseIndex`/`isFinalPhase` (nil for plain timers and for alarms scheduled before 1.0.4; keep them optional). Buttons are hidden while alerting (the full-screen alert has its own).

**The intents compile into both the app and the widget, but `perform()` always runs in the app's process.** So `LiveActivityIntents.swift` (in `Shared/`, excluded from Clip/Messages) only forwards to `LiveActivityActions`, which exists twice under the same name: the real one in `sharedTimer/` (TimerStore + `AlarmController.rescheduleAwaiting`/`TimerArming.armAwaiting` + CloudKit/watch push + a **main-actor** `.externalTimerStoreChange` post — every on-device lesson from the sequence-intent history below applies), and a no-op stub in `sharedTimerWidget/` that only exists so the shared file compiles there. Keep their signatures identical; never put logic in the stub (the widget must not reach AlarmController/CloudKit).

**Pause keeps the AlarmKit alarm alive in `.paused` instead of cancelling it** (`AlarmController.armPaused`, plain and sequence paths): the presentation now carries `AlarmPresentation.Paused(resumeButton:)`, so the card stays on screen showing Resume, like the Clock app. Resume cancels and re-creates from `pausedRemaining` (normal path). Pausing a sequence keeps only the current phase's alarm (paused) and drops the pre-armed future ones; resume re-arms the window. Deliberately **no `pauseButton` on `AlarmPresentation.Countdown`** — that would let the system pause the alarm without running our code and desync TimerStore. AlarmKit can't edit a paused alarm's duration, so when the paused time changes (extend while paused) or no alarm exists, `armPaused` schedules a fresh alarm for the new remaining time and pauses it immediately; the remaining time each alarm was paused at is recorded per alarm id in the App Group (`alarmPausedRemaining`), since `Alarm` doesn't expose elapsed time. Verified on device by `pausingKeepsTheAlarmPausedAndResumeRearmsIt` and `extendingWhilePausedReplacesThePausedAlarmWithTheNewLength`.

### Home-screen widget buttons, recents, Control Center control

The **Single Timer** widget shows `WidgetTimerControls` (`sharedTimerWidget/LiveActivityControls.swift`): Pause/Resume + Stop/Next/Cancel while running, **Repeat** (`RepeatTimerIntent`) once finished, nothing while a sequence is pending. The **All Timers** list shows Pause/Resume only per row (no Stop, so a busy home screen can't mis-tap it). These are the same intents as the Live Activity buttons (`Shared/LiveActivityIntents.swift`, run in the app's process); `TimerStore.save` already reloads widget timelines.

`Shared/RecentTimersStore.swift` (app + widget, excluded from Clip/Messages) keeps the last 6 distinct plain **timers** (label + length + toggles; countdowns and sequences are ignored), most recent first. Its `RecentTimer` has a hand-written lenient `init(from:)` — same reason as the `SavedSequenceStore` warning below: it's decoded as a root array. It's recorded by `ContentView.startNew` (New Timer sheet, recent chips, Quick Actions), `StartTimerIntent` and `LiveActivityActions.startRecent`, and drives three surfaces, all refreshed by `RecentTimersSync.refresh()` (app-only):
- the **Recent** chips at the top of `NewTimerSheet` (tap = start as-is; long-press = remove),
- two **dynamic Quick Actions** (type `recent:<id>`, routed by `ContentView.openQuickAction`) after the static New Timer / New Countdown,
- the **Control Center / Action button control** `StartRecentTimerControl` (widget extension; title "Start Pasta 8m" from a `ControlValueProvider`) whose button runs `StartRecentTimerIntent` — a `LiveActivityIntent`, so it runs in the app's process where AlarmKit exists, without opening the app. Kind string must match `RecentTimersSync.controlKind`.

### Scheduled start (`TimerPayload.scheduledStartDate`, `isPending(at:)`) — sequence-only

"Start later" (`NewSequenceSheet`'s own "Start later" toggle + date picker) lets a **sequence** begin phase 0 at a picked future moment instead of immediately. Deliberately **not** available for a plain timer/countdown (`TimerFieldsView`, used by `NewTimerSheet` and `sharedTimerMessages/TimerComposeView`, carries no such toggle) — a product-scope decision, not a technical limit; the model/display plumbing below would work identically for a plain timer/countdown if that ever changes. `scheduledStartDate: Date?` is the payload field (nil = starts now, the default/back-compat value everywhere); `isPending(at: Date = Date())` (`scheduledStartDate != nil && scheduledStartDate! > date`) is the only thing that reads it — pure and date-parameterized like every other `TimerModel.swift` state check.

`scheduledStartDate` now travels in sequence links as `start` (Unix seconds) and in CloudKit as `scheduledStartDate` (Date), as well as local JSON persistence. Messages, App Clip, and the web fallback display pending state. The deliberately flattened Watch model still ignores it.

**The finish alert is armed at creation, unconditionally — never deferred.** iOS gives the app no background execution, so "wait until the start time, then arm the alert" would silently fail to alert anyone who schedules a start and doesn't reopen the app before it. Instead, `composeSequence` computes phase 0's `endDate` as `start + firstPhase.duration` up front, so a pending sequence is scheduling-wise identical to today's existing "countdown to a target date 3 months out" — `AlarmController`/`NotificationScheduler` already handle an arbitrarily-far `endDate` correctly with zero code changes. `scheduledStartDate` is **never mutated after creation** (no "pending → running" transition is persisted); everything downstream just derives "is it still pending" from the clock each time it's asked. A start at or before "now" (picker sat open past the picked time) is clamped to `nil` in `composeSequence` — never a payload whose own scheduled start already lies in the past. `repeated(at:)` also clears `scheduledStartDate` unconditionally (belt-and-suspenders — nothing currently calls `repeated()` on a still-pending payload, but `isPending()` must never lie about a payload that function just started running).

The custom `TimerActivityAttributes` Live Activity (both toggles off case) waits for the real start time on purpose: `LiveActivityController.start(for:)` has an `isPending()` guard at its top (one `Shared/` file compiled by `sharedTimer` and `sharedTimerMessages`; `sharedTimerClip` doesn't compile `LiveActivityController.swift` at all — see the mutation-sites paragraph above) because a Live Activity's no-update budget is ~8h — one started days before the sequence even begins would die long before it matters. `ContentView.checkForNewlyExpired`'s existing 1s tick also tracks a `pendingIDs` set (mirroring `armedIDs`'s own self-initializing pattern) and starts that Live Activity the moment a pending payload's start passes while the app sits foregrounded — **but only that**, never the full `armAlerts` (see the `stopIntent`-style gotcha below for why).

**AlarmKit's own Live Activity, fixed (originally a documented known gap): `Alarm.Schedule.fixed(_:)`, checked against the real `.swiftinterface`, not just the public docs.** The naive `countdownDuration: .init(preAlert: payload.remaining, postAlert: payload.duration)` — correct for every other payload — makes AlarmKit's lock-screen/Dynamic-Island countdown appear the instant a pending sequence is scheduled, days before it starts, since `remaining` there is wait-plus-duration. Fixed by passing `schedule: .fixed(payload.endDate)` (already start + phase 0's duration) alongside `countdownDuration: .init(preAlert: payload.duration, postAlert: payload.duration)` **only when `payload.isPending()`** — every other payload (later phases, plain timers/countdowns, Repeat) keeps the original `preAlert: payload.remaining`, no `schedule`. Confirmed on device: with this combination the alarm sits with no lock-screen/Dynamic-Island presence at all until the real start time, then AlarmKit's own `.scheduled → .countdown` transition kicks in automatically — no app code needed to "activate" it, unlike the custom Live Activity's `pendingIDs` tick. This combination isn't documented anywhere (beta API, verified by behavior not by docs) — if a future SDK version changes what `schedule` + `countdownDuration` together mean, re-verify with the same device test: create a pending sequence 2 minutes out with a 1-minute phase 0, confirm nothing shows for 2 minutes and the alarm rings at +3, not +4.

**Corollary: `checkForNewlyExpired`'s `pendingIDs` tick must never call the full `armAlerts` for a payload that just started.** AlarmKit is already transitioning that alarm from scheduled to counting down on its own at that exact moment; `armAlerts` → `reschedule` unconditionally cancels the existing alarm first (same as the `alarmKitOwnsAlert` gotcha elsewhere in this doc), which would race and potentially clobber AlarmKit's own automatic transition. The tick only ever calls `LiveActivityController.start` directly, gated on `!AlarmController.ownsAlert(for:)` — the both-toggles-off notification was already correctly scheduled for `endDate` at creation and needs no nudge.

**"Start Now"** (row swipe/context menu, and `TimerDetailView`'s button row) lets someone skip the wait on a pending sequence — reuses `TimerPayload.repeated(at:)` rather than a new model function: a pending sequence is already sitting at phase 0/loop 0, so "reset to phase 0/loop 0, `endDate = now + phase0.duration`, clear `scheduledStartDate`" (what `repeated()` already does) is exactly "start now." Distinct from `repeatTimer` (used on a *finished* payload) — a pending payload was never alerting, so there's no alarm/vibration to stop and no `armedIDs` entry to touch.

Existing mutations on a pending sequence: **Pause and Extend are hidden** (row swipe/context menu, `TimerDetailView`'s button row, and the phone-side `WatchSyncController` message handler) — pausing or extending something that hasn't started yet doesn't mean anything; **Delete is the only control**, and doubles as "Cancel" (no separate cancel concept). The `WatchSyncController` guard is real, not defensive-for-no-reason: `pushCurrentState` doesn't filter sequences out, so a pending sequence's flattened phase-0 view can appear on the watch looking like an ordinary timer, and the watch itself has zero pending awareness — the guard has to live on the phone side of that relay. `advancedSequence`/`persist`'s prune already treat a pending sequence correctly with no changes needed: `endDate` is in the future, so neither one does anything to it.

Display: `SkyCard` ("Scheduled" status word, big digits show the start time itself — deliberately **not** a ticking countdown to it, which read as urgent/already-running and defeated the point of the state; `endText` reads "starts …") and `TimerDetailView` (with matching pending/phase context in Messages and App Clip recipients). The visual treatment (still reusing the existing gradient/sky look, no dedicated art) is a placeholder — a proper design pass is still open, per the usual "pitch mockups before design work" rule.

### Sequence timers (`SequencePhase`/`SequenceInfo`, `TimerPayload.advancedSequence(at:)`)

An ordered list of `SequencePhase` (label, kind, duration, own `alarmEnabled`/`vibrationEnabled`), looped `loopCount` times, carried as `TimerPayload.sequence: SequenceInfo?`. Fully free-form in the compose UI (`sharedTimer/NewSequenceSheet.swift`'s `NewSequenceSheet`/`PhaseEditView`) — add, delete, reorder, and edit any phase; Pomodoro and Intermittent Fasting are two `SequenceTemplate`s that just seed the initial name/phases/loop count as worked examples of the concept, alongside a blank "Custom" template, not a fixed pair of modes. `NewSequenceSheet` wraps each `SequencePhase` in a sheet-private `DraftPhase: Identifiable` (a UUID) for stable `ForEach` row identity across insert/delete/reorder — `SequencePhase` itself still carries no `id`, so this costs no model change. A built custom sequence can be saved (`SavedSequenceStore.swift`, `sharedTimer`-only — a local blueprint, rather than a running payload; sharing preserves the running sequence but does not import a saved template) and re-selected from "Start from" alongside the built-in templates. `NewSequenceSheet`'s `SequenceSource` enum (`.builtin(index:)` / `.saved(id:)`) identifies the current selection instead of a bare array index — needed once the "Start from" list is backed by a mutable (deletable) saved-sequence array, where an index would silently point at the wrong entry after a deletion.

**`SavedSequenceStore.loadAll()` decodes `[SavedSequence]` with no custom `init(from:)`, and fails silently to `[]` on any decode error.** Unlike `TimerPayload` (whose hand-written `init(from:)` back-compats every field it's ever added), `SavedSequence` and `SequencePhase` have never needed one — `SequencePhase` has only ever lived nested inside a running `TimerPayload` before, where `TimerPayload`'s own back-compat init absorbed the surrounding decode. A saved sequence is the first place `SequencePhase` is the *decode root*. **Adding a field to either struct without `decodeIfPresent` + a default silently deletes every user's saved sequences on the next launch after update** — write the back-compat init the same day you add the field, not after.

**Shared sequence follow-up (2026-10-07):** running sequences now round-trip through links and CloudKit; see the wire-format section below. `WatchShared/TimerModel.swift` remains deliberately separate and ignores sequence/start fields, retaining only the current-phase WatchConnectivity mirror. Saved templates and compose UI remain main-app-only.

`label`, `duration`, `kind`, `alarmEnabled`, `vibrationEnabled` are `var` on `TimerPayload`, not `let`: for a sequence-owning payload these are the "currently materialized phase" projection, overwritten in place by `advancedSequence(at:)` at each phase transition. This is what lets every existing consumer — `AlarmController`, `NotificationScheduler`, `LiveActivityController`, `TimerAlarmMetadata`, `SkyCard`, `TimerDetailView`, the widget's `nextRefresh`/`Text(timerInterval:)` — keep reading "whichever phase is running now" with zero sequence-awareness of their own; none of those files' scheduling/rendering internals were touched to add this feature.

**Sequences only ever advance by re-derivation, never by a running state machine**: iOS has no background execution, so nothing can run code exactly at a phase boundary while the app is closed or the phone is locked. `advancedSequence(at:)` is a pure, idempotent, bounded (`phases.count * loopCount` iterations, never clock-bound) function that walks forward from whatever phase is currently stored to whichever phase should be current *right now* — correct no matter how long the app was backgrounded, even having missed several whole phases. It must be called, in this order, at every point that already re-derives state on a live read, and **before** `AlarmController.reconcileRepeat`: `ContentView.onAppear`, the `scenePhase` foreground handler, and `checkForNewlyExpired`'s 1s tick (the only hook that sees a live zero-crossing while the app stays foregrounded — fire `AlarmPlayer`/`VibrationPlayer` off the *pre-advance* state first, exactly as for a plain timer, then advance). `TimerDetailView` holds its own `@State` copy of the payload and does the same advance-and-reseed on its own tick, independent of `ContentView`. Don't reintroduce a "current phase" that advances by a single `+1` step per event — a short-phase sequence (Pomodoro) backgrounded for hours would desync.

**Pre-armed phase window (1.0.4) — every sequence phase occurrence gets its own AlarmKit alarm, armed ahead of time.** `AlarmController.performSequenceReschedule` arms the current phase plus up to `sequenceWindow` (8) total upcoming occurrences from `TimerPayload.upcomingSequencePhases(limit:)` (pure, chains end dates exactly like `advancedSequence`, unit-tested to match it). Each occurrence has its own id, `AlarmController.phaseAlarmID(timerID:globalIndex:)` (globalIndex = loopIndex·phases.count + phaseIndex). Before this, a sequence had one alarm the app re-armed at each boundary, so tapping the primary **Stop** (not "Next") left nothing armed for the next phase — on a locked phone the rest of the sequence never rang. Rules that keep it safe:
- **An earlier occurrence's alarm is never cancelled while it's `.alerting`** — the alert for the phase that just finished is index current−1 once advanced, so re-arming after an advance can't kill it (the structural fix for the "alert flashes and disappears" bug below). Earlier occurrences still counting down / scheduled / paused **are** cancelled, along with every occurrence ≥ current that isn't kept and the legacy single `alarmID(for:)` from 1.0.3: confirmed on device that "Next" tapped on the Live Activity mid-phase otherwise left the skipped phase's alarm running — a second Lock Screen card that would still have rung.
- **An existing alarm whose `.fixed` date and `preAlert` match (1s tolerance) is kept**, not cancelled and re-created, so re-arming an unchanged sequence is a no-op.
- **The current phase keeps the plain-timer config** (`preAlert: remaining`, no schedule) unless pending; only future occurrences whose countdown window still lies in the future get `schedule: .fixed(end)` + `preAlert: duration` — the one `.fixed` combination confirmed on device (the pending-sequence case below). Never `.fixed` a phase whose countdown would already be running.
- Scheduling stops at the first future-phase failure (`maximumLimitReached` is logged). The window only refills when the app reschedules this sequence (open/foreground/Next/any mutation) — a sequence longer than 8 occurrences left untouched still runs out of pre-armed alarms. Phases with both toggles off are never pre-armed (they only get a notification while current).
- `AdvanceSequenceIntent` carries `phaseIndex` (the tapped alert's global index, `-1` = stored phase, which is also what 1.0.3-scheduled alarms decode to) and starts the occurrence *after the tapped one* via `TimerPayload.materializingPhase(globalIndex:startingAt:)` — needed because after a Stop the stored payload can lag the alert being tapped. A tap on an alert the stored payload already moved past doesn't step. Deleting a sequence must use `AlarmController.clear(_ payload:)` (needs the shape to enumerate phase ids); `EndSequenceIntent` uses `cancelSequenceAlarms(for:)`, which also cancels the ringing final alert.
- `rescheduleAwaiting` now goes through the per-id serializer (`Serializer.runAndWait`) instead of bypassing it, since a sequence reschedule is up to ~9 AlarmKit calls and must not interleave with a concurrent foreground one.

**`checkForNewlyExpired`'s tick and `TimerDetailView`'s own tick advance-and-persist but do NOT re-arm while `AlarmController.alarmKitOwnsAlert(for:)` is true** (`ContentView.apply(_:action:rearm: false)`, `TimerDetailView.onSequenceAdvance`). History (confirmed on device, pre-1.0.4): when every phase shared one alarm id, the tick's `apply` → `reschedule` cancelled AlarmKit's just-presented alert within about a second — it flashed and disappeared, and any Stop/Next tap lost the race (this is *why* Stop and "Next" once looked identical). The tick used to skip the advance entirely, which left the UI stuck on "Finished" and nothing armed for the next phase while the app stayed open. Per-phase ids make the cancel structurally impossible now, but the next phases are pre-armed anyway, so the tick still keeps its hands off AlarmKit while an alert is up. `onAppear`/`scenePhase` keep the full re-derive + re-arm (safe under the rules above). `alarmKitOwnsAlert` differs from `ownsAlert`: it additionally requires `AlarmManager.shared.authorizationState == .authorized`, since `ownsAlert` alone stays true even when AlarmKit is denied/unavailable and `reschedule` fell back to `NotificationScheduler` — nothing interactive to protect there, so the tick re-arms normally in that case.

`TimerPayload.repeated(at:)` is sequence-aware: for `sequence != nil` it resets to phase 0/loop 0 (re-materializing phase 0's fields), never "repeat whichever phase happened to be current." `AlarmController.reconcileRepeat` skips any `sequence != nil` payload unless it's already exhausted (`loopIndex == loopCount`) — an un-advanced mid-sequence payload also reads as `isFinished`, and must not be mistaken for "user tapped Repeat on AlarmKit's panel." `AlarmController.scheduleAlarm` suppresses AlarmKit's own "Repeat" secondary button entirely for any sequence phase (including the final one): AlarmKit's `.countdown` secondary-button behavior can only restart the *same* `postAlert` duration, which would silently re-run the phase that just finished instead of advancing — all sequence restarts go through the sequence-aware `repeated()` instead, reached only from in-app UI.

`TimerStore.persist`'s 24h-expired prune projects a `sequence != nil` payload through `advancedSequence()` before checking its `endDate` against the cutoff — the raw stored `endDate` is only the current phase's, so a legitimate multi-day sequence sitting on a stale un-advanced phase would otherwise look long-expired and get deleted.

**`stopIntent` vs `secondaryIntent` — confirmed on-device, two different `AlarmConfiguration` parameters with very different effects.** A sequence phase's alarm originally wired `stopIntent` (the PRIMARY Stop control's action) to an `AdvanceSequenceIntent`, meant to arm phase 2+ without the app foregrounding when the user tapped Stop on a fired alert. On a physical device this did not behave as "runs when Stop is tapped" — giving the alarm a non-nil `stopIntent` at all made AlarmKit treat the whole alarm as background-resolvable and run the intent immediately when it fired, dismissing it with no full-screen alert and no user interaction, for every sequence phase, both locked and unlocked. **`stopIntent` must always stay `nil`.**

The correct hook, per the real AlarmKit `.swiftinterface` (`AlarmManager.AlarmConfiguration.init` — check `.../iPhoneOS.sdk/System/Library/Frameworks/AlarmKit.framework/Modules/AlarmKit.swiftmodule/arm64e-apple-ios.swiftinterface` directly rather than trusting the public docs/headers, same as the `AlertConfiguration.AlertSound` check elsewhere in this doc), is the separate `secondaryIntent` parameter, paired with `AlarmPresentation.Alert.secondaryButtonBehavior: .custom` (a distinct case from `.countdown`) and a real `secondaryButton` on that Alert. `scheduleAlarm` now gives a sequence phase a "Next" secondary button (`.custom` behavior, `secondaryIntent: AdvanceSequenceIntent(...)`) instead of the bare title-only alert it had before — that bare alert (no secondary button at all) was **also separately confirmed broken**: it rendered fine on the lock screen but never presented at all when the device was unlocked (app foregrounded or another app frontmost), matching a plain timer/countdown's alert (which always had a working secondary button) working correctly in every state. A `secondaryButton` appears to be required for AlarmKit's non-lock-screen presentation to render at all, independent of the `stopIntent` bug above.

`AdvanceSequenceIntent`'s purpose is unchanged — advance to the next phase and arm its alarm without the app foregrounding — but it originally called the fire-and-forget `AlarmController.reschedule` and returned immediately. **Confirmed on device that this never actually armed the next phase**: `reschedule` only kicks off a detached Task via the per-id serializer and returns; that's fine for `reschedule`'s normal callers since the app process stays alive regardless, but the system may tear down a `LiveActivityIntent`'s execution the instant `perform()` returns, before the detached Task gets to run `AlarmManager.schedule` at all. Fixed with `AlarmController.rescheduleAwaiting(for:) async` — the same cancel/schedule work, run inline and awaited directly by `perform()` instead of fired off unawaited. This was the real "unverified execution budget" question from the original design note, and the answer was "the code never gave it a chance to use any budget," not a genuine platform limit — worth remembering if a future `LiveActivityIntent` needs to call back into `AlarmController`: **use `rescheduleAwaiting`, never the bare `reschedule`, from any intent's `perform()`.**

**Do not put sequence-advance (or any custom) logic on `stopIntent`** — that parameter is confirmed to suppress the interactive alert entirely. Use `secondaryIntent` + `secondaryButtonBehavior: .custom` for any future "custom action on a button tap" need, and await the actual work inside `perform()` rather than triggering a fire-and-forget path.

**One more `AdvanceSequenceIntent` gap, confirmed on device: tapping "Next" looked like a no-op specifically when SharedTimer was the frontmost app, but worked when a different app was frontmost.** A `LiveActivityIntent` runs in-process — when the app happens to already be foreground, that's the *same* process as the live `ContentView`, whose `@State timers` array `AdvanceSequenceIntent.perform()` never touches (it writes straight to `TimerStore`). `TimerStore`/AlarmKit were actually updated correctly in both cases; only `ContentView`'s in-memory copy (and an open `TimerDetailView`'s local `payload`) went stale, and nothing refreshed it until the app backgrounded and refocused — which is exactly what a different-app-frontmost round trip does via the normal foreground reload, hiding the bug there. Fixed by posting `.externalTimerStoreChange` at the end of `perform()` — the same notification `AppDelegate`'s push handler and `WatchSyncController` already post for this identical class of problem ("a mutation landed in `TimerStore` while this view is already foregrounded"), and both `ContentView` call sites already listen for it. **Any future code that mutates `TimerStore` from outside `ContentView`'s own mutation path (`apply`/`applyMutation`) — an intent, a background task, anything running in-process without going through those — must post `.externalTimerStoreChange`, or the change is invisible until the next background/foreground cycle.**

**The button is "Next" or "Cancel," never both — dynamic on a single `secondaryButton` slot.** `AlarmPresentation.Alert`'s primary Stop control is a fixed OS button (`Alert.stopButton` is deprecated/unused in the current SDK — no label or action of ours is possible on it), and the Alert has exactly one `secondaryButton`. So a sequence phase's alert shows "Next" (`AdvanceSequenceIntent`) on every phase except the final one, where it switches to "Cancel" (`EndSequenceIntent`, marks `loopIndex = loopCount` and cancels every phase alarm via `AlarmController.cancelSequenceAlarms(for:)`) — computed in `scheduleAlarm` as `isFinalSequencePhase = phaseIndex == phases.count - 1 && loopIndex == loopCount - 1`, matching exactly the condition `advancedSequence(at:)` uses to decide a sequence is exhausted (TimerModel.swift). **Cancelling mid-sequence, before the final phase, is not available from this alert** — only the primary Stop, which just dismisses that alert; the following phases keep ringing on schedule from the pre-armed window (within its 8 occurrences). This is a hard platform limit (confirmed via the swiftinterface), not a missing feature — don't try to add a third button.

**Resolved — the app-frontmost bug was never "the intent doesn't run," it was an undefined-behavior SwiftUI state write.** Confirmed on device with a temporary `print` at the top of each `perform()`: both intents *do* run correctly while SharedTimer is frontmost (console showed `AdvanceSequenceIntent fired for ...` then later `EndSequenceIntent fired for ...` for the same sequence's final phase — the dynamic button routing itself was never broken). Alongside those prints, SwiftUI logged **"Publishing changes from background threads is not allowed."** `LiveActivityIntent.perform()` runs off the main thread; the `.externalTimerStoreChange` post was happening on that same background thread, and `NotificationCenter` delivers synchronously on the posting thread — so `ContentView`'s `.onReceive` closure (`timers = TimerStore.loadAll()`, a `@State` write) was executing off-main-actor too. That's undefined behavior for SwiftUI state, not a guaranteed no-op, which is why it looked inconsistent/like nothing happened rather than crashing outright. **Fix: both intents now wrap the notification post in `await MainActor.run { ... }`.** `TimerStore.save` and the `AlarmController` calls before it don't need the same treatment — they don't touch SwiftUI state directly. The diagnostic `print`s have been removed now that this is settled; if a similar "the button doesn't seem to do anything while foregrounded" report ever recurs for a different `LiveActivityIntent`, check for this exact pattern before re-diagnosing "does the intent even run" from scratch.

**A second, unrelated bug hid behind the first: `AdvanceSequenceIntent` originally reused `TimerPayload.advancedSequence(at:)`, the same date-based re-derivation function `onAppear`/`scenePhase`/the foreground ticks use.** That function is correct for those callers — "figure out whatever phase should be current after being away for an unknown amount of time," chaining each phase's `endDate` off the *previous* phase's stale boundary so a backgrounded app catches up exactly right. It is the wrong function for an explicit "Next" tap, whose meaning is "start the next phase now," not "re-derive from elapsed time." With short phase durations (easy to hit while testing), any real delay between the alert firing and the tap — trivially more likely while fumbling with the phone in the foreground than reacting to a locked-screen alert — made `advancedSequence` walk through several phases, or exhaust the sequence outright, in one call. This is what actually produced the reported "foreground vs. locked" difference; it was never a foreground/locked code fork. Fixed with `TimerPayload.steppedToNextPhase(at:)` (`TimerModel.swift`) — a literal one-phase-forward step timed from the moment of the call, used only by `AdvanceSequenceIntent`. Every other sequence-advance call site correctly keeps using `advancedSequence(at:)`; don't switch them.

### Edit a timer (`TimerPayload.edited`, `sharedTimer/EditTimerSheet.swift`)

Main app only: detail-screen pencil + row context menu "Edit…". Scope (product decision, 2026-10-07): label + Alarm/Vibrate toggles for timers (time changes stay on +1:00/Extend — `TimerFieldsView(showsTimerLength: false)`), plus target date for countdowns (disabled while paused, `targetDateDisabled`). **Sequences are never editable** — their label/toggles are the current phase's projection; `edited` returns them unchanged and the UI hides Edit. A countdown keeps its original start (`endDate - duration`, ≤ now) and only `duration` changes, so the ring still means "elapsed since created" and `AppDelegate.notifyIfExtended` (needs unchanged `duration`) never announces an edit as an extend. An annual edit re-anchors `AnnualRecurrence` in its own time zone — but only when the target moved ≥1s, so renaming a clamped occurrence (Feb 29 shown as Feb 28, DST-shifted time) can't silently move the anchor. Goes through `applyMutation(…, action: "edited")`: no new wire/CloudKit field.

**AlarmKit presentation signature.** Two paths keep an existing alarm when its *time* matches — `armPaused` (paused at the same remaining) and annual fixed-date alarms — and would leave a renamed/re-toned alarm stale. `scheduleAlarm` records `"label|alarmEnabled"` per alarm id in the App Group (`alarmPresentationSignature`, pruned like `alarmPausedRemaining`); both keep-paths also require it to match (missing = mismatch, one re-create). This lives in AlarmController, not the edit call sites, so an edit arriving via CloudKit is covered too. Sequence `matchesPrearmed` doesn't check it — add it there if sequences ever become editable.

### Siri / Shortcuts

`sharedTimer/TimerIntents.swift` provides Start Timer, Start Countdown, Pause, Resume, Extend, and Time Remaining. `TimerShortcuts` donates six App Shortcuts with static phrases plus timer-name phrases for the four existing-timer actions. Numeric minutes cannot be phrase-interpolated: Extend asks for them separately; Shortcuts can supply a configured value. All `perform()` methods run on the main actor to match the app's timer model/store isolation.

`Shared/TimerChoice.swift` is the `AppEntity` shared by the app and widget (excluded from Clip/Messages). Keep its type name and string IDs stable so saved widget configurations and Shortcuts still resolve. `TimerChoiceQuery` supports name search with exact matches preferred and duplicates returned for Siri to disambiguate. Suggestions derive current sequence phases and omit finished/cancelled timers; identifier lookup still returns finished timers so a configured widget keeps showing them.

`TimerIntentActions` reloads by ID, re-derives sequences before inspecting state, and rejects mutations on missing/finished/scheduled timers. Pause/Resume are idempotent; Extend preserves paused state and only changes the current sequence phase. Time Remaining is read-only and returns seconds (current phase, or wait + first-phase duration for a pending sequence) alongside state-aware spoken feedback. Mutations save, await `TimerArming.armAwaiting`, push watch state, refresh shortcut parameters, post `.externalTimerStoreChange` on the main actor, then await `CloudSyncController.pushUpAwaiting`. The cloud write is best-effort on failure; it does not undo the local mutation. Existing fire-and-forget `pushUp` callers retain their behavior.

Device test runs should run `sharedTimerTests/sharedTimerTests` and `sharedTimerTests/AlarmKitDeviceTests` separately: the unit suite backs up/restores the App Group store, while the two Siri integration tests write their own temporary timers. Running both suites concurrently can interfere with those temporary timers. Each device test awaits teardown even if an intent throws. Confirmed on the network-connected iPhone 14 Pro (2026-10-07): 51 unit + 13 AlarmKit tests pass. Voice invocation, two-account CloudKit delivery, and paired Watch delivery remain manual checks. Individual timer Spotlight indexing is implemented; see below.

### Spotlight timer search

`sharedTimer/TimerSpotlightIndex.swift` owns the app-only Core Spotlight index. Stable identifiers use the timer domain plus `TimerPayload.id`; search metadata never carries a timer snapshot. `TimerSpotlightEntry` derives the current phase, static state/end-date descriptions, phase-name keywords, and expiry (24h after the final end; indefinite for a paused unfinished timer). Finished results older than 24h are omitted.

`AppDelegate` starts the indexer. `TimerStore.didPersist` is an optional process-local callback installed only in the main app; its default is nil in extensions. The callback runs under the write lock and **only schedules a task**: never read/write the store or await indexing there. The indexer's main-actor worker reads the newest store after the lock is released, coalesces requests, applies incremental updates/deletes, and reconciles its whole domain once per launch or system reindex request. Index errors leave timer operations successful and cause a full retry on the next change/foreground. Background Siri/Live Activity/widget intents await indexing before returning. Extension changes reconcile when the main app next runs; no new cross-process wake mechanism is implied.

`ContentView` refreshes on foreground, timer-choice/finish changes, and pending→running transitions. ### Shared sequence links / CloudKit (local follow-up, 2026-10-07)

`TimerSequenceWire` encodes UTF-8 JSON `{ "version": 1, "sequence": SequenceInfo }` in `seq` URL query data and the CloudKit `Timer.sequenceData` Bytes field. `start` uses Unix seconds; `scheduledStartDate` and `updatedAt` use CloudKit Date fields. Existing scalar fields remain for older clients (they see only a single-phase snapshot). New clients reject malformed/unsupported sequence envelopes instead of flattening them, validate finite scalar values and bounded indices, and advance overdue sequences on link/record decode without changing their mutation stamp. Wire limits: 64 phases, 99 loops, 512 UTF-8 bytes per nonempty phase label, durations 1s–365d, and a 64 KiB envelope.

Both row and detail Share actions open `ShareTimerSheet`, which prepares a CloudKit URL with `ckshare`, falling back to the full sequence snapshot after the existing four-second timeout. `createShare` reuses existing owner/participant shares, rather than trying to create a second share for a root record; timeout/completion delivery is serialized on main. Cloud conflict retries include changed keys that were cleared to nil, so resume/repeat cannot accidentally preserve a stale pause/start field. The `Timer` fields `sequenceData` (Bytes), `scheduledStartDate` (Date/Time), `updatedAt` (Date/Time) and `recurrenceData` (Bytes) were deployed to the production schema on 2026-10-07. **Any future new CloudKit field must be deployed to production before its release** ([Apple's guidance](https://developer.apple.com/documentation/CloudKit/deploying-an-icloud-container-s-schema)) — production builds can't create fields. Two-account CloudKit delivery is still unverified.

Explicit Next/Cancel actions await CloudKit push before returning; Cancel stamps an immediately finished, silent snapshot (Repeat restores the stored phase toggles). Pure clock-driven `sequenceAdvanced` actions save/re-arm locally and never push/attribute a user mutation; every recipient derives the same phase schedule, avoiding stale projections overwriting remote pauses/steps/extensions. Messages reloads authoritative accepted/reopened shares into its visible state. App Clip remains snapshot-only; both recipient views follow phase boundaries, display loop/scheduled context, and respect phase alarm/vibration toggles.

`NotificationScheduler.requests` builds up to eight per-phase requests with `timerID` and `sequenceGlobalIndex` userInfo. Fixed `.phase.0`…`.phase.7` slots make cancellation bounded. A process-local generation/lock prevents stale authorization callbacks from re-arming a cancelled schedule. The main app passes occurrences already covered by AlarmKit as exclusions; quiet phases and scheduling failures use notifications. `TimerStore.isAlarmKitArmed` is true when **any** current/upcoming phase is covered, so simply opening a mixed sequence in Messages/Clip preserves the main app's combined alert window. User mutations inside Messages still cannot move AlarmKit until the main app handles that change (existing extension limitation). Notification Repeat/Stop resolves the stable timerID instead of a slot ID.

Remote deletion may arrive after an extension removed the payload. `AlarmController.clear(id:)` intersects currently scheduled alarms with derived occurrence IDs across the bounded shared format (64×99), cancelling the entire sequence even without stored phase definitions. Payload-based teardown still handles larger local drafts.

Verified: 77 unit/Spotlight/widget/sequence tests on the iPhone 14 Pro and simulator; 18 AlarmKit device tests (including actual mixed notification/AlarmKit coverage and remote deletion after payload removal); two UI tests, including scheduled import → Start Now → Pause → Extend → Resume → Delete. Eight deterministic web timing tests (`node --test docs/tests/timer.test.cjs`) cover phase/loop catch-up, pause, pending start, finish, old links, invalid versions, and text-only labels; four headless Chrome captures verify layouts at 390×844. The browser skill was read, but its Node REPL execution tool was unavailable, so the local headless browser was used. CI runs the web tests. Messages/Clip on-device presentation and two-account delivery remain manual checks.

### Annual countdowns / Calendar import (local follow-up, 2026-10-07)

`AnnualRecurrence` anchors Gregorian month/day/hour/minute/second in an IANA time zone. February 29 clamps to February 28 in non-leap years and returns to February 29 in leap years. `Calendar.nextDate(.nextTime, .first)` resolves missing/repeated DST times. `advancedRecurrence` catches up missed years without changing `updatedAt`; `advancedSequence` delegates plain annual payloads to it, so existing recipient/widget/Siri projections remain consistent. A pause freezes the current occurrence, and Extend/Resume only shift that occurrence; the annual anchor stays unchanged. Repeat uses the next anniversary. Explicit Next Year is idempotent by its occurrence end stamp; widget Pause and Watch mutations project a missed annual occurrence before changing it. Stop clears recurrence and all its future alarms.

Store JSON carries optional `recurrence`. Version-one `annual` query JSON and CloudKit `Timer.recurrenceData` Bytes preserve the anchor; invalid/unknown envelopes and sequence/annual combinations are rejected. Deployed to production with the other 1.0.4 fields (2026-10-07). Older apps and the deliberately separate Watch model retain only the current occurrence. Two-account propagation remains unverified.

Annual alerts use two `.alarm(schedule: .fixed(...))` configurations with alert-only presentations and **no countdown duration**. Using the countdown initializer/presentation with a nil duration was rejected by AlarmKit on device. Two stable slots per Gregorian year handle extensions over New Year's Eve; matching fixed alarms stay armed, and rollover preserves an already-alerting occurrence. The current+following-year window refills on foreground/finish/mutations; Timer must run at least yearly to keep refilling. Notification fallback excludes covered dates (not years, because two occurrences can share a year). Remote ID-only deletion intersects all bounded derived IDs; test teardown clears both alarms and notifications.

Main-app `CalendarImportSheet` uses a `CalendarCountdownSource` protocol: production wraps `EKEventStore.requestFullAccessToEvents` and future-year queries; tests inject permission/event/error sources. `NSCalendarsFullAccessUsageDescription` is generated for both app configurations. Permission is requested only inside the import picker; denial/restriction/error/empty states let people enter dates or retry/open Settings. Event choices use identifier+start date so repeated event instances have distinct rows. Only title/start/time zone are copied; no event is modified or linked for ongoing updates. Birthday/simple unbounded annual rules preselect Repeat yearly; relative or finite rules stay one-off. The main creation sheet is item-driven by `TimerKind`, avoiding stale initial kind on first opening.

`t.html` follows the same annual clock rules using Intl time-zone parts. Countdown Add to Calendar downloads UTF-8 `.ics`: escaped text, 75-byte CRLF folding, UTC one-off dates, annual RRULE (February's last day for leap birthdays), self-contained VTIMEZONE and explicit UTC exceptions for spring gaps/autumn repeats. The export includes 30 years of current rules; future government changes can require re-export. A shifted first occurrence uses RDATE/EXDATE without shifting the later annual wall time. Paused countdowns hide export. `docs/tests/timer.test.cjs` has 19 cases; external ical.js parsing/ten-year expansion and a mobile-sized headless capture were also checked locally (no repo dependency added).

Verified: 93 non-AlarmKit tests on iPhone 14 Pro/simulator, 25 real AlarmKit tests, five device UI flows and 19 web tests. New device cases cover annual fixed dates, pause/resume, Next Year/Stop, remote deletion, year-crossing extensions, real quiet notifications, and widget Pause after a missed year. Device access is coordinated with the MirrorNotes peer thread to prevent overlapping tests/foreground launches.

### Watch app (`WatchSyncController.swift`, both sides)

App Groups do **not** sync between an iPhone and its paired Watch (separate devices, separate
container filesystems) — verified against Apple's own guidance, not assumed. So the watch app
is not a fifth `TimerStore` reader; it's a thin `WatchConnectivity` mirror of whatever
`sharedTimer/WatchSyncController.swift` last pushed via `updateApplicationContext`. Mutations
made on the watch relay back to the phone as a `WCSession` message and are applied there
through the exact same `TimerStore`/`AlarmController`/`LiveActivityController`/
`CloudSyncController.pushUp` sequence every other surface uses — the watch target itself never
touches any of those (ActivityKit isn't even available on watchOS), and doesn't carry
`TimerStore.swift`/`NotificationScheduler.swift`/`LiveActivityController.swift`/
`CloudSyncController.swift` at all. `WatchSyncController.pushCurrentState()` (phone side) is
called explicitly at every `TimerStore`-mutating point in `ContentView.swift` and
`AppDelegate.swift` — same "explicit call at each mutation site, never automatic" invariant
`CloudSyncController.swift`'s own header documents, for the same reason (this file, too, must
never be reachable from `TimerStore.swift` itself).

### Watch complication / Smart Stack (local follow-up, 2026-10-07)

`sharedTimerWatchWidget` is a watchOS WidgetKit extension embedded **inside the Watch app**, with circular, rectangular/Smart Stack, and inline families. `WatchShared/` compiles into both Watch targets; it contains the Watch-only model, `WatchTimerCache`/`WatchTimerSnapshot`, deep links, and accessory layouts.
